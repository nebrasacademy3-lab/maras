# توافق الاختبارات مع Windows — 23 سبتمبر 2026

التغييرات في ملفات الاختبار فقط. لم تتغير صلاحيات ملفات التوكن أو مفاتيح الاستعادة، ولا O_NOFOLLOW، ولا معالج الإشارات أو الحماية أثناء التشغيل.

## اختبارات تعمل على النظامين

- مسار ملف JavaScript القادم من URL يُحوّل بـfileURLToPath؛ استخدام pathname كان ينتج C:\C:\… على Windows ولا يشغّل preflight الحقيقي أصلًا.
- ملف توكن التجديد الاصطناعي يستخدم مسارًا مطلقًا بصيغة النظام. اختبار traversal يحتفظ بـ.. حرفيًا ويتحقق من رفضه؛ لا يستخدم join الذي يزيله قبل وصوله إلى الدالة.
- روابط الدلائل تستخدم junction على Windows وsymlink على Ubuntu. بهذا تعمل فعليًا اختبارات منع تجاوز أصل التخزين، ومنع إخفاء المفتاح تحت مجلد النسخ الاحتياطي، ورفض أسلاف الدليل المرتبطة دون حاجة صلاحيات إنشاء file symlinks في Windows.
- اختبار التخزين الخاص يفحص رابطًا في المكون الوسيط ورابطًا في المكون الأخير على النظامين. الرابط الأخير junction على Windows وfile symlink على Ubuntu؛ كلاهما يمر عبر isSymbolicLink في التنفيذ نفسه.
- منع الكتابة فوق ملفات موجودة ورفض hard links للاستعادة ما زالا يعملان على Windows، وقد فُصلا عن اختبار O_NOFOLLOW.
- اختبار خروج العامل برمز نجاح غير متوقع ما زال يتأكد من خروج المشرف بالفشل وإنهاء جميع العمليات التابعة. على POSIX يتأكد أيضًا من تشغيل SIGTERM handler للتابع. Windows ينهي العملية مباشرةً، ولذلك يتوقع غياب marker الخاص بذلك handler فقط، مع استمرار فحص توقف العملية الحقيقي.
- فحص منع مفاتيح الإنتاج في اختبارات CI يشغّل نقطة الدخول الحقيقية مع قيم اصطناعية، ويتأكد من الرفض وتنقيح المخرجات قبل أي عمل شبكي أو ترحيل.

## تجاوزات Windows المحددة

- اختبارات private mode 0600 وO_NOFOLLOW وFIFO لملفات Gemini؛ كانت متجاوزة أصلًا على Windows وأصبحت أسباب التجاوز صريحة.
- اختبار قراءة مفتاح الاستعادة عبر private POSIX modes، واختبار O_NOFOLLOW ضد file symlink. NTFS ACLs لا تعادل بتات صلاحيات POSIX ولا يدعم Windows ضمان O_NOFOLLOW نفسه.
- ثلاث حالات تتطلب التقاط SIGTERM/SIGINT فعليًا، وفترة سماح ثم SIGKILL، وحالة process groups/descendants. Node على Windows ينهي العملية عند kill دون إرسال هذه الإشارات القابلة للالتقاط إلى JavaScript.

كل تجاوز مربوط صراحةً بـprocess.platform === "win32" ومعه سبب ظاهر في TAP. لا توجد catch عامة تحول فشلًا إلى نجاح، ولا تجاوز للمجموعة كاملة.

## تغطية الإنتاج في CI

ملف .github/workflows/quality.yml يشغّل job الويب على ubuntu-latest وNode 22 ويشغّل tests/*.test.mjs كاملة. لذلك تعمل حالات POSIX المذكورة هناك دون skip؛ وjob مستقل يفحص container الإنتاج لعزل PDF. لم يُغيّر هذا التحديث Workflow أو ضوابط runtime لإخفاء فشل محلي.

نجاح Windows لا يعادل تشغيل Ubuntu أو إثبات ACLs للبيئة الحقيقية. النتيجة المحلية محفوظة في .data/windows-platform-tests.log؛ ننتظر CI نفسه لإثبات ضوابط النظام المستضيف للإنتاج.
